# ADR-0004: Sync via CloudKit private database with end-to-end encrypted fields

**Status:** Proposed · **Date:** 2026-10-25

## Context

Some browsers sync through **two** backends, Apple's CloudKit and a vendor database. Running two backends doubles complexity and puts user data on a vendor server.

## Decision

- Use **CloudKit private database + `CKSyncEngine`** (macOS 14 / iOS 17) only. Users' data lives in *their* iCloud, at no server cost to us, and it works on every Apple device.
- Mark URL and title fields as `encryptedValues` (end-to-end encrypted with the user's iCloud keys).
- Sync unit = one record per Space and one per Node. Conflict rule: last-writer-wins per field, with ordering kept by fractional indices.
- Non-Apple platforms (if ever) get an optional self-hostable sync server later. That's not v1.

## Consequences

- Requires a paid Apple Developer account and iCloud entitlements (`com.apple.developer.icloud-services`), which means an `embedded.provisionprofile`.
- Sync can't be tested in CI without an iCloud account, so we test the merge logic as a pure function and run the CloudKit integration in a manual QA pass.
